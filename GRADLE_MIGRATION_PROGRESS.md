# Gradle Build System

This document describes the Gradle build configuration for the LOCKSS 2.x system.

## Architecture

### Convention Plugins (buildSrc)

The `buildSrc/` directory contains Gradle convention plugins that replace Maven's parent POM inheritance:

| Plugin | Purpose |
|--------|---------|
| `lockss-java-conventions` | Base Java configuration (JDK 17, repositories, publishing, test artifacts) |
| `lockss-spring-boot-conventions` | Spring Boot 3 + OpenAPI code generation |
| `lockss-pom-bundle-conventions` | Dependency-only BOM projects |

### Version Catalog

All dependency versions are centralized in `gradle/libs.versions.toml`:

```toml
[versions]
spring-boot = "3.4.1"
cxf = "4.0.4"
antlr = "4.9.3"
# ... etc

[libraries]
spring-boot-starter-web = { module = "org.springframework.boot:spring-boot-starter-web" }
cxf-jakarta-rt-frontend-jaxws = { module = "org.apache.cxf:cxf-rt-frontend-jaxws", version.ref = "cxf" }
# ... etc
```

## Key Implementation Details

### Legacy Jetty Transformation

`lockss-core` uses Eclipse Transformer to convert legacy Mortbay Jetty (5.1.5) from `javax.*` to `jakarta.*` namespaces:

```kotlin
// lockss-core/build.gradle.kts
val transformedDepsDir = file("${project.layout.buildDirectory.get()}/transformed-deps")

val transformJavaxDeps by tasks.registering(JavaExec::class) {
    mainClass.set("org.eclipse.transformer.cli.JakartaTransformerCLI")
    // Transforms lockss-legacy-org-mortbay-jetty to jakarta namespace
}

dependencies {
    api(fileTree(transformedDepsDir) { include("*.jar") })
}
```

### OpenAPI Code Generation

Spring Boot services use OpenAPI Generator with post-processing:

```kotlin
// In build.gradle.kts
openapi {
    specFile.set(file("src/main/resources/swagger/swagger.yaml"))
    basePackage.set("org.lockss.laaws.config")
}
```

The convention plugin:
1. Runs OpenAPI Generator with Spring Boot 3 / Jakarta EE settings
2. Executes `scripts/swaggerProcessing.sh` to rewrite imports
3. Adds generated sources to the Java source set

**Important**: The `swaggerProcessing.sh` scripts must:
- Fix imports to use shared DTOs from `lockss-util-rest` (e.g., `ApiStatus`, `PollerSummary`, `PollDesc`)
- Fix imports in **all** generated files including `*ApiController.java` (not just `*Api.java` and `*ApiDelegate.java`)
- Delete generated model files that duplicate classes in `lockss-util-rest`:
  ```bash
  rm -f ${MODEL_DIR}/PollerSummary.java
  rm -f ${MODEL_DIR}/PollDesc.java
  rm -f ${MODEL_DIR}/ApiStatus.java
  ```

### Log4J2 Configuration

LOCKSS uses Log4J2 with a custom `L4JLogger` class. Spring Boot's default logging must be excluded to prevent conflicts. This is handled automatically by the `lockss-spring-boot-conventions` plugin:

```kotlin
// In buildSrc/src/main/kotlin/lockss-spring-boot-conventions.gradle.kts
configurations.all {
    exclude(group = "org.springframework.boot", module = "spring-boot-starter-logging")
    exclude(group = "ch.qos.logback", module = "logback-classic")
    exclude(group = "org.apache.logging.log4j", module = "log4j-to-slf4j")
}
```

**Why this matters**: Spring Boot's `spring-boot-starter-logging` includes:
- `logback-classic` (Logback as the default logger)
- `log4j-to-slf4j` (routes Log4J2 calls to SLF4J)

These conflict with LOCKSS's direct use of Log4J2. The `log4j-to-slf4j` bridge causes:
```
java.lang.ClassCastException: org.apache.logging.slf4j.SLF4JLogger cannot be cast to org.lockss.log.L4JLogger
```

The exclusions must be global (`configurations.all`) because `spring-boot-starter-logging` is pulled in transitively from multiple starters (web, security, json, etc.).

### BuildInfo / build.properties Generation

The `BuildInfo` class (`lockss-util-core`) reads build metadata from `org/lockss/componentresources/build.properties` at runtime. In Maven, this file was generated by the antrun plugin during the `initialize` phase. In Gradle, this is handled by the `lockss-java-conventions` plugin's `generateBuildInfo` task.

**Implementation**:

```kotlin
// In buildSrc/src/main/kotlin/lockss-java-conventions.gradle.kts
val generateBuildInfo by tasks.registering(WriteProperties::class) {
    group = "build"
    description = "Generate build.properties for BuildInfo"

    val buildInfoDir = project.layout.buildDirectory.dir("resources/main/org/lockss/componentresources")
    destinationFile.set(buildInfoDir.map { it.file("build.properties") })

    // Project properties
    property("build.name", project.name)
    property("build.version", project.version.toString())
    property("build.groupId", project.group.toString())
    // ... more properties

    // Build environment (timestamp formatted like Maven's antrun)
    val buildTimeMillis = BuildTimestamp.nowMillis()
    property("build.timestamp", BuildTimestamp.format(buildTimeMillis))  // dd-MMM-yy HH:mm:ss zzz
    property("build.rawtimestamp", buildTimeMillis.toString())

    // Git info
    property("build.git.branch", gitBranch.get())
    property("build.git.commit", gitCommit.get())
    property("build.git.dirty", gitDirty.get())
}

tasks.named("processResources") {
    dependsOn(generateBuildInfo)
}
```

**Helper class** (`buildSrc/src/main/kotlin/BuildTimestamp.kt`):
The `BuildTimestamp` object provides timestamp formatting compatible with Maven's antrun output. This is necessary because Gradle precompiled script plugins have limited access to `java.util` and `java.text` classes at compile time.

**Properties generated**:
- `build.name`, `build.artifactId`, `build.groupId`, `build.version`
- `build.timestamp` (formatted: `04-Dec-25 16:39:11 PST`)
- `build.rawtimestamp` (milliseconds since epoch)
- `build.git.branch`, `build.git.commit`, `build.git.dirty`
- `build.host`, `build.user.name`, `build.os.*`
- `build.java.version`, `build.java.vendor`, etc.

### Resources from Source Directories

`lockss-core` has resources (XML mapping files, keystores, DTDs) located in `src/main/java` and `src/test/java` instead of the standard `src/main/resources` and `src/test/resources`. In Maven, this is handled via `<resources>` and `<testResources>` configuration.

**Important**: Do NOT modify `sourceSets.main.resources` with `include` patterns - this will interfere with the default processing of `src/main/resources` and prevent files like `DefaultBundle.properties` and `i18n.properties` from being copied.

Instead, use a separate Copy task:

```kotlin
// Copy non-Java resources from src/main/java
// Using a separate task avoids interfering with src/main/resources processing
val copyMainJavaResources by tasks.registering(Copy::class) {
    from("src/main/java")
    into(layout.buildDirectory.dir("resources/main"))
    include(
        "**/*.xml",           // mapping files (externalmap.xml, etc.)
        "**/*.keystore",      // keystores (lockss.keystore)
        "**/*.dtd",           // DTDs
        "**/errorpagetemplate.html",
        "**/urlrewriter.js"   // IA/WERA javascript
    )
}

tasks.named("processResources") {
    dependsOn(copyMainJavaResources)
}

// For test resources, modifying sourceSets is safe
sourceSets {
    test {
        resources {
            srcDir("src/test/java")
            exclude("**/*.java", "**/*.tdb")
        }
    }
}
```

**Critical resources that must be on the classpath:**
- `org/lockss/util/externalmap.xml` - Required by `ExternalizableMap`
- `org/lockss/plugin/lockss.keystore` - Required by `PluginManager` for plugin verification
- `DefaultBundle.properties`, `i18n.properties` - Required for i18n (from `src/main/resources`)
- Various plugin XML files in test directories

### Test Artifact Dependencies

Projects that need test utilities from other modules must explicitly depend on their `testArtifacts` configuration:

```kotlin
dependencies {
    // Access test classes from lockss-core (MockArchivalUnit, ConfigurationUtil, etc.)
    testImplementation(project(":lockss-core", configuration = "testArtifacts"))

    // Access test classes from lockss-spring-bundle (SpringLockssTestCase4, etc.)
    testImplementation(project(":lockss-spring-bundle", configuration = "testArtifacts"))
}
```

The `testArtifacts` configuration is defined in `lockss-java-conventions.gradle.kts` and produces a `-tests.jar` containing test classes and resources.

### ANTLR Generation (lockss-tdb-tools)

Custom two-pass generation for separate lexer/parser grammars:

```kotlin
// Generate lexers first (produce .tokens files)
val generateAntlrLexers by tasks.registering(JavaExec::class) {
    mainClass.set("org.antlr.v4.Tool")
    args = listOf("-visitor", "-package", "org.lockss.tdb", ...)
}

// Generate parsers (depend on lexer tokens)
val generateAntlrParsers by tasks.registering(JavaExec::class) {
    dependsOn(generateAntlrLexers)
    args = listOf("-lib", antlrOutputDir.absolutePath, ...)
}
```

## Adding a New Spring Boot Service

1. Create `build.gradle.kts`:

```kotlin
plugins {
    id("lockss-spring-boot-conventions")
}

group = "org.lockss.laaws"
version = "1.0.0-SNAPSHOT"

openapi {
    specFile.set(file("src/main/resources/swagger/swagger.yaml"))
    basePackage.set("org.lockss.laaws.myservice")
}

dependencies {
    api(project(":lockss-spring-bundle"))
    // Service-specific dependencies
}

docker {
    imageName.set("laaws-myservice")
    restPort.set(24680)
    uiPort.set(24681)
}
```

2. Update `scripts/swaggerProcessing.sh` to use configurable paths:

```bash
GENERATED_DIR="${GENERATED_DIR:-src/generated/java}"
API_DIR="${GENERATED_DIR}/org/lockss/laaws/myservice/api"
MODEL_DIR="${GENERATED_DIR}/org/lockss/laaws/myservice/model"
```

3. Add to `settings.gradle.kts`:

```kotlin
include("laaws-myservice")
```

## Known Test Issues

### TestLogger.testFunc (lockss-core) / TestLockssLogger.testFunc (lockss-util-core)

This test fails with:
```
java.lang.NullPointerException: Cannot invoke "org.lockss.log.ListAppender.getMessages()"
because the return value of "org.lockss.log.TestLockssLogger.getListAppender()" is null
```

**Impact**: 1 test failure each in lockss-core and lockss-util-core (2 total failures)

**Status**: Pre-existing test infrastructure issue, not caused by Gradle migration.

#### What the Test Does

The `testFunc()` test verifies that LOCKSS's custom logging system works correctly:

1. Creates loggers at different log levels (`test.critical`, `test.error`, `test.warning`, etc.)
2. Logs messages at various severity levels
3. Captures log output using a custom `ListAppender` that collects messages in-memory
4. Verifies the messages match expected output based on configured log levels
5. Tests dynamic reconfiguration by changing log levels via LOCKSS config

#### The ListAppender Component

The test uses a custom Log4J2 appender (`org.lockss.log.ListAppender` in `src/test/java`) that:
- Is annotated with `@Plugin(name = "ListAppender", ...)` for Log4J2 plugin discovery
- Stores log messages in a `List<String>` instead of writing to console/file
- Provides `getMessages()` to retrieve captured messages and `reset()` to clear them

#### How Configuration is Supposed to Work

LOCKSS uses Log4J2's **composite configuration** feature. In `log4j2.component.properties`:

```properties
log4j.configurationFile=log4j2-lockss.xml,log4j2-lockss-test.xml,log4j2-lockss-project.xml,log4j2-lockss-local.xml
```

Log4J2 loads and **merges** all these files. The intent:
- `log4j2-lockss.xml` - Main production config (Console, File appenders)
- `log4j2-lockss-test.xml` - Test-specific config (ListAppender)

#### The Configuration Conflict

There are **two** `log4j2-lockss-test.xml` files:

| Location | Content | Size |
|----------|---------|------|
| `src/main/resources/log4j2-lockss-test.xml` | Empty placeholder | 134 bytes |
| `src/test/resources/log4j2-lockss-test.xml` | Has ListAppender | 1046 bytes |

**Main version (empty):**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!-- Empty config, tests supply their own version of this -->
<Configuration>
</Configuration>
```

**Test version (with ListAppender):**
```xml
<Configuration status="WARN">
  <Appenders>
    <ListAppender name="ListAppender"/>
  </Appenders>
  <Loggers>
    <Logger name="test" level="DEBUG">
      <AppenderRef ref="ListAppender"/>
    </Logger>
    <!-- ... more test loggers ... -->
  </Loggers>
</Configuration>
```

#### Root Cause Analysis

The design intent was:
1. Production builds include an empty `log4j2-lockss-test.xml` (no-op)
2. Test builds should have `src/test/resources` ahead on classpath, so the test version "wins"

However, Log4J2's composite configuration doesn't work by classpath ordering - it **merges all files found**. The merge strategy may not properly combine both `log4j2-lockss-test.xml` files.

**Additional Factor - Plugin Discovery**: The `ListAppender` class is in `src/test/java`, meaning Log4J2's plugin system may not discover the `@Plugin`-annotated class during test execution if the configuration is loaded before the test classes are scanned.

#### Possible Fixes

1. **Rename the test config file** to avoid collision (e.g., `log4j2-test-appenders.xml`)
2. **Use system property** to explicitly point to the test config
3. **Add Log4J2 annotation processor** to generate plugin metadata at compile time
4. **Force configuration reload** in the test's `@BeforeAll` after ensuring test resources are on classpath
